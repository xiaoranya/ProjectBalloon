# 灾难恢复

本节定义正式部署的故障场景与响应原则。

## 通用响应流程

```text
检测事件
  -> 识别受影响服务与影响
  -> 保留日志与当前状态
  -> 应用干扰最小的恢复操作
  -> 验证健康检查
  -> 验证比赛特定正确性
  -> 记录事件备注
```

## API 故障

症状：

- 网关返回 5xx。
- 参赛者无法提交或查看页面。
- 管理控制台不可用。

响应：

- 检查 Nginx 与 API 健康。
- 必要时重启受影响的 API 服务。
- 验证数据库、Redis、RabbitMQ 与 RustFS 连通性。
- 确认中断期间的提交未被部分接受而没有队列任务。

## Judge Worker 故障

症状：

- Worker 在线数下降。
- Judge 队列深度增长。
- 提交长时间保持 `pending` 或 `judging`。

响应：

- 检查 Worker 主机 CPU、内存、磁盘与沙箱日志。
- 重启失败的 Worker 服务。
- 确认 RabbitMQ 未确认消息返回队列或完成。
- 复核 `system_error` 提交。
- 可用时增加更多 Judge 主机。

## RabbitMQ 故障

症状：

- 无法发布 Judge 任务。
- Worker 无法消费任务。
- 队列指标不可用。

响应：

- 保留 RabbitMQ 日志与数据目录。
- 数据完整时重启 RabbitMQ。
- 验证队列、绑定与未确认消息。
- 如需要管理员操作，将处于 `pending` 或过期 `judging` 状态的提交重新入队。

## Redis 故障或清空

症状：

- 记分板缓存缺失。
- 限流计数器重置。
- SSE 扇出降级。

响应：

- 重启 Redis。
- 从 PostgreSQL 重建记分板与 first blood 缓存。
- 验证公共与管理员记分板。
- 若 PostgreSQL 状态完整，则继续比赛。

## PostgreSQL 故障

症状：

- API 无法读写权威数据。
- 无法安全接受提交。

响应：

- 数据库完整性不确定时停止 API 写入。
- 保留 PostgreSQL 日志与数据目录。
- 先尝试正常重启。
- 如需恢复，遵循 [备份与恢复](backup-restore.md)。
- 恢复后验证提交与判定一致性。

## RustFS 故障

症状：

- 题目附件不可用。
- Worker 无法获取测试数据。
- 提交代码或日志无法归档。

响应：

- 检查 RustFS 服务与磁盘。
- 安全时重启。
- 验证桶可用性与对象哈希。
- 若测试数据读取大面积失败，暂停判题。
- 确认损坏后恢复 RustFS 对象。

## 打印机故障

症状：

- CUPS 任务失败或打印机离线。
- 打印队列增长。

响应：

- 检查打印机电源、纸张、网络与 CUPS 状态。
- 打印机恢复后重试失败任务。
- 对紧急队伍打印请求使用手动下载回退。
- 保持审计状态准确。

## Screen 或 Live 故障

症状：

- Screen 心跳停止。
- OBS 浏览器源无法加载 live 页面。
- 公共展示陈旧。

响应：

- 检查网关与页面路由。
- 刷新浏览器源或重连 Screen 客户端。
- 验证 live 页面的 token 有效性。
- 动态展示无法快速恢复时使用静态回退页面。

## 比赛暂停标准

出现以下情况时考虑暂停或延长比赛：

- 提交在较长时间内无法接受。
- 判题不可用时间长到影响比赛公平。
- 许多队伍的题目描述或 Clarification 访问不可用。
- 数据正确性不确定。

暂停与延长决定必须被审计。
