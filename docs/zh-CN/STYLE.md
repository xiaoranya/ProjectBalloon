# 文档写作规范

本规范定义了 ProjectBalloon 文档在已发布的文档网站上的写作方式，适用于 `docs/` 下属于手册的所有页面：使用手册、运维手册与参考页面。内部工程笔记（架构、开发、需求）遵循相同的结构规则，但不作为面向用户的手册发布。

## 先明确读者

每个页面必须在开头段落说明面向谁、解决什么问题：

- **使用手册**面向通过 Web 界面使用平台的人：选手、比赛管理员和现场工作人员。
- **运维手册**面向在赛事现场安装、运行和恢复部署的人。
- **参考页面**（配置变量、API 契约）面向需要精确取值或端点的人。
- **内部笔记**（架构、开发、需求）面向修改代码库的人。

不要假设读者已经阅读过仓库。尽量描述读者“做什么、看到什么”，而不是代码如何实现。

## 页面结构

每个已发布页面都使用相同的骨架：

1. **Frontmatter**——YAML 形式的 `title` 与 `description`：

   ```yaml
   ---
   title: 选手指南
   description: 介绍选手如何注册、提交代码、解读判定结果，以及使用榜单、Clarification 与打印功能。
   ---
   ```

2. **H1 标题**——与 `title` 一致，使用名词短语（如「选手指南」），不要写成句子。
3. **引言**——用一两句话说明读者对象与页面内容。可加「开始之前」一行链接前置条件。
4. **任务式正文**——按读者操作顺序组织，用 `##` 分节、`###` 分子任务。
5. **参考资料**——用表格或列表给出精确值（路由、权限、判定、变量）。
6. **「另见」**——页面末尾列出相关页面。

## 语气与表达

- 使用祈使句：「导入队伍」「验证健康检查端点」。
- 使用主动语态和现在时。
- 段落要短，列表要单用途。
- 如果读者必须按顺序操作，用编号步骤，而不是堆砌要点。
- 已发布页面不要包含仓库内部状态类内容（「Status」「Document Map」「Documentation Rules」「Source Layout」），这类内容放到本文档或仓库 README。
- 避免以「本文档描述……」开头，直接说明结果。

## 链接

- 使用相对 `docs/` 目录的链接，而不是仓库根路径：
  - 正确：`[安装指南](ops/install.md)`
  - 错误：`docs/ops/install.md`
- 链接文字要可读（如「参见安装指南」），不要写裸路径。
- 保留 `.md` 扩展名，保证 GitHub 与文档站点都能解析。
- 每页中同一个目标只链接一次。

## 代码与命令

- 命令放入围栏代码块，不要带 `$` 提示符。
- Shell 输出用 `text` 围栏，结构化内容用 `yaml`/`json`/`toml`。
- 手册中的命令与路径面向已部署系统（`/etc/project-balloon`、`sudo systemctl ...`）。开发命令属于开发章节。
- 绝不包含真实密钥、令牌或密码。

## 术语

- 产品名称：**ProjectBalloon**。
- 路由、权限码、环境变量和判定结果在两种语言中都保持英文：`/contests`、`CONTEST_MANAGE`、`PROJECT_BALLOON_SESSION_TTL_SECONDS`、`ACCEPTED`。
- 尽量与界面文案保持一致。
- 「选手（Contestant）」指队员；「工作人员（staff）」指拥有工作台权限的赛事人员；「管理员（administrator）」指使用管理后台的用户。

## 语言与镜像

- 英文为规范版本；每个英文页面在 `zh-CN/` 下有相同相对路径和结构的对应中文镜像。
- 两个版本应在同一次变更中同步更新。
- 机器生成的内容（OpenAPI 契约）不做镜像。

## 保持文档同步

- 行为、配置、路由或工作流变更时，应在同一变更中更新相关手册页面。
- 页面变更后，检查所有指向它和从它出发的链接。
- 发布前按下方「评审清单」逐项检查。

## 评审清单

- [ ] Frontmatter 包含 `title` 与 `description`。
- [ ] 首段说明读者对象与范围。
- [ ] 有顺序的操作使用编号步骤；列表为单用途要点。
- [ ] 链接为 `docs/` 相对路径，文字可读，且不带 `docs/` 前缀。
- [ ] 已发布页面中没有仓库内部状态或布局说明。
- [ ] 同一次变更中更新了中文镜像。
- [ ] 术语与界面及本规范一致。
