# 架构概述

本文档描述 ProjectBalloon（一个 XCPC/ICPC 竞赛平台）的第一版架构。需求来源文档为 `docs/requirements/project-balloon-requirements.md`。

## 目标

平台必须支持可预测恢复行为的正式离线局域网竞赛。

主要指标：

- 至少 500 支在线队伍，约 1,000 到 1,500 名用户。
- 每分钟约 10,000 次请求，即 167 RPS。
- 峰值提交吞吐量为每分钟 100 到 300 次提交。
- 初始判题能力为 30 到 60 个并发判题槽。
- 完全离线部署，不依赖公共 CDN、公共镜像仓库、公共软件包镜像或第三方 SaaS 服务。
- 覆盖从赛前配置到赛后 Resolver、颁奖、导出和归档的完整 XCPC/ICPC 流程。

## 架构风格

第一版采用模块化单体业务后端加独立判题 Worker 集群。

后端实现使用 Rust Cargo 工作区。API 是运行在 Tokio 上的 Axum 模块化单体；调度器/outbox 分发器承载在 API 进程中。判题执行仍是可单独部署的 Rust Worker。业务模块是按功能分组的 Rust 模块，而不是 controller/service/repository 类的副本。PostgreSQL 访问使用显式 SQLx 查询和事务边界。

```text
参赛者 / 管理员 / 大屏页面 / 直播页面
  -> Nginx
  -> Web 前端 + API 后端
  -> PostgreSQL / Redis / RabbitMQ / RustFS
  -> 判题调度器
  -> 判题 Worker 集群
  -> 沙箱运行时
```

该结构在保持业务一致性简单的同时，将判题执行风险与 CPU 负载从 API 和数据库工作负载中隔离。

## 组件职责

| 组件 | 职责 |
|---|---|
| Nginx | 局域网入口、静态文件服务、反向代理、请求大小/时间限制 |
| Web 前端 | 参赛者 UI、管理控制台、大屏页面、直播页面、Resolver、颁奖 |
| API 后端 | 业务 API、认证、直接权限访问控制、竞赛数据、提交、榜单、审计 |
| 判题调度器 | 提交任务调度、重试协调、Worker 可见性 |
| 判题 Worker | 编译、沙箱运行、收集结果/日志、上报判题结果 |
| PostgreSQL | 权威业务数据和竞赛结果 |
| Redis | 热点缓存、榜单缓存、SSE 扇出支持、限流计数器 |
| RabbitMQ | 判题任务队列、重试队列、死信队列 |
| RustFS | 面向题目资源、测试数据、提交归档、日志、导出、打印 PDF 的 S3 兼容对象存储 |
| CUPS | 向局域网打印机投递文本打印 |
| Prometheus/Grafana | 指标采集与仪表盘 |
| Loki/Promtail | 集中式日志 |

## 业务模块

即使最初以单个服务部署，后端也应按模块组织。

P0 模块：

- 身份与直接权限访问控制
- 队伍与账号管理
- 竞赛管理
- 题目与测试数据管理
- 提交管理
- 判题调度集成
- ICPC/XCPC 榜单
- 封榜与快照
- Resolver 快照与事件
- Clarification 与公告
- 打印请求
- 气球任务
- 颁奖规则与获奖名单
- 大屏控制
- 直播页面与令牌
- 审计日志
- 健康检查与导出

## 请求与事件流

常规参赛者提交流程：

```text
提交源代码
  -> API 校验竞赛状态、语言、大小和速率限制
  -> API 将提交存入 PostgreSQL，并将源码归档存入 RustFS
  -> API 向 RabbitMQ 发布判题任务
  -> Worker 消费任务，仅在建立持久结果写入意图后 ACK
  -> Worker 在沙箱中编译并运行
  -> Worker 将日志/产物写入 RustFS
  -> Worker 向 API 或持久化层上报结果
  -> 更新榜单、气球、统计和 SSE 事件
```

榜单更新流程：

```text
判定定稿
  -> 更新权威提交/判定行
  -> 增量重算受影响的队伍/题目状态
  -> 更新 Redis 榜单缓存
  -> 需要时持久化快照
  -> 发布 SSE 事件刷新 UI
```

## 实时投递

SSE 是默认的实时机制。

推荐的事件通道：

- 竞赛公告
- Clarification 通知
- 提交状态更新
- 榜单失效/更新提示
- 大屏命令
- 直播事件
- Resolver 控制事件
- 气球与打印任务更新

SSE 载荷在公共、大屏和直播通道上应避免敏感信息。源代码、IP 地址、内部备注和私有 Clarification 内容绝不能发送到公共通道。

## 可用性原则

- PostgreSQL 是事实来源。
- Redis 数据可重建，且不得是竞赛结果的唯一副本。
- RabbitMQ 队列必须对判题任务使用 ACK、重试和死信处理。
- Resolver 必须使用竞赛定稿后生成的不可变快照。
- 二进制发布包必须固定且可复现。
- 运维人员必须拥有一键健康检查、备份、恢复、启动、停止和状态脚本。

## 初始非目标

除非被明确提升，以下不是第一版目标：

- OI/IOI 计分。
- 交互题。
- 只输出题（output-only）。
- 代码相似度检测。
- 公共训练系统。
- 多租户公共 OJ 运营。
