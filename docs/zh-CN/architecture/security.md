# 安全

本文档总结第一版的安全需求。

## 威胁模型

平台会运行不受信任的参赛者代码，并存储官方比赛数据。主要风险：

- 沙箱逃逸或主机被攻破。
- 正式比赛期间数据损坏。
- 未授权的管理员操作。
- 源代码、IP、内部备注或私有 Clarification 的公开泄露。
- 通过题目描述、公告或 Markdown 造成的 XSS。
- 因过量提交、打印请求或刷新流量导致的拒绝服务。

## 判题安全

必需的控制措施：

- 禁用运行时网络访问。
- 强制 CPU、内存、进程、文件与输出限制。
- 隔离文件系统。
- 只读挂载测试数据。
- 每次运行后清理临时目录。
- **生产 / 比赛部署**：Judge 容器不得挂载 Docker socket，也不得以 privileged 容器运行。
- **开发沙箱例外**：在本地开发与 CI 中，Worker 可以作为 sibling-docker 容器运行（挂载 `/var/run/docker.sock`），前提是 (a) Worker 进程以加入 `docker` 组的非 root 用户运行，(b) Worker 绝不从用户可控输入构造 shell 或 Docker CLI 命令字符串，只能通过 Rust `bollard` 客户端使用类型化的 Docker API 参数，并且 (c) 每个沙箱容器都以无网络、只读根文件系统、`no-new-privileges`、PID 限制、非 root UID/GID 以及自动清理的方式创建。威胁模型：用户提交的代码是不可信边界，且始终停留在沙箱容器内；Worker 代码属于可信基。
- 正式部署中，Judge Worker 必须与数据库主机分离。

Judge Worker 应以与所选沙箱实现兼容的最低主机权限运行。

## Web 安全

必需的控制措施：

- 使用 Argon2id 对新密码进行哈希。仅在迁移期间接受遗留 BCrypt 哈希，并在登录成功后升级它们。
- 所有工作人员 API 使用直接、可组合的账户权限。
- 基于共享的 PostgreSQL 审计状态应用登录限流，避免通过切换 API 实例绕过限制。
- 提交限流。
- Clarification 限流。
- 打印请求限流。
- 使用签名的 double-submit CSRF token 保护每个基于 Cookie 认证的状态变更请求。
- 通过参数化访问防止 SQL 注入。
- 通过输出转义与 Markdown 净化防止 XSS。
- 上传类型、大小与扩展名校验。
- 公共 / Live / Screen API 与管理 API 严格分离。

## 浏览器认证

Rust API 使用不透明的服务端会话：

- 浏览器通过 `HttpOnly`、`SameSite=Lax` 的 Cookie 接收 `PB_SESSION`。
- PostgreSQL 仅存储随机会话 token 的 SHA-256 摘要。
- 生产环境设置 `PROJECT_BALLOON_SECURE_COOKIES=true`，并在请求到达 API 之前终止 TLS。
- 登录会轮换会话，并撤销浏览器此前出示的任何会话。
- 登出在清除 Cookie 之前删除服务端会话。
- 管理员禁用、权限变更和密码重置会在同一事务中撤销受影响用户的会话。认证还会检查账户状态与访问指纹，作为纵深防御。
- 被标记为需要重置密码的用户在修改密码之前只能访问认证流程；受保护的功能处理器必须调用 `require_password_ready`。
- 功能处理器通过 `AuthContext::require_permission` 强制授权；前端中的路由可见性绝不是授权边界。

登录前，前端从 `GET /api/auth/csrf` 获取 CSRF token。它在每个状态变更请求中通过 `X-XSRF-TOKEN` 发送返回值。可读的 `XSRF-TOKEN` Cookie 与请求头必须匹配，服务器会验证 token 签名。`PROJECT_BALLOON_CSRF_SECRET` 必须是独立生成的部署机密。除非为本地开发设置 `PROJECT_BALLOON_ALLOW_DEV_CSRF_SECRET=true`，否则已检入的开发值会被无条件拒绝；并且它绝不能与安全 Cookie 一起被接受，因此默认部署无法使用公开已知的密钥签署 CSRF token。

## 工作人员账户管理

只有已完成必需密码变更的已认证 `SUPER_ADMIN` 才能调用 `/api/admin/staff-accounts`。

- 创建工作人员时会将用户名规范化为小写，并分配所请求的直接权限集；`SUPER_ADMIN` 是一种用户类型，而不是角色。
- `TEAM` 账户由队伍生命周期管理，不能通过工作人员端点创建或修改。
- 新密码与管理员重置的密码始终使用 Argon2id，并要求用户在下次登录时选择新密码。
- 超级管理员不能移除或禁用自身的访问权限。
- 工作人员访问变更使用 PostgreSQL 事务级 advisory lock 加行锁。这会将管理员创建与降级串行化，防止锁反转，并在并发请求下至少保留一个启用的超级管理员。
- 用户变更、权限替换、比赛范围清理、会话撤销与审计插入原子提交。

比赛管理员范围替换也使用单个事务。它会锁定目标账户，针对未删除的权威行校验每个比赛，批量替换分配，并记录操作者。无效的比赛 ID 绝不能部分清除或修改先前的范围。

审计日志访问仅限于超级管理员。过滤与分页值受限，排序选择采用白名单，所有 SQL 值均保持参数化。审计响应可能包含用户 ID 与请求 IP，绝不能通过公共、Live、Screen 或参赛者 API 暴露。

## 比赛访问

比赛读取在数据库查询中使用单一可见性策略，使分页计数与返回的行不会不一致：

- 公开比赛可匿名读取；
- 队伍与比赛管理员访问从权威分配表解析；
- 被显式分配了运维权限的账户可以读取私有比赛，而不会获得配置权限；
- 不可访问与不存在的比赛详情都返回 `CONTEST_NOT_FOUND`，以避免私有比赛枚举。

比赛管理员在变更事务内部再次被授权。权限变更会撤销活动会话，比赛分配与每次变更在同一事务中校验。
只有超级管理员可以创建比赛或检查软删除记录。

## 队伍身份

队伍授权基于标识符。已认证的参赛者账户通过 `team_accounts` 与且仅与一个队伍关联；可变的用户名、显示名、队名与学校绝不视为身份。队伍范围的查询在返回私有比赛或实时数据之前，先在 PostgreSQL 中解析并约束这一关系。

密码仅在账户创建、批量导入与显式重置时接受。它们持久化前使用 Argon2 哈希，绝不存储或返回明文，密码重置会撤销账户的现有会话。

## 敏感数据规则

绝不通过公共记分板、Screen 或 Live API 暴露：

- 提交源代码。
- 登录名（除非有意展示）。
- 密码哈希。
- 内部备注。
- 对其他队伍的私有 Clarification 回复。
- 请求 IP。
- 管理员操作日志。
- 备份路径与凭据。

## Token 与机密处理

- 只提交 `.env.example` 文件。
- 将真实 `.env` 文件存放在 Git 之外。
- 不记录原始会话或 CSRF token。
- 如果彩排期间共享过 live 广播 token，在正式比赛前轮换它们。
- 为 PostgreSQL、Redis、RabbitMQ、RustFS、Grafana 与应用服务使用不同的凭据。
- 不在健康检查输出中打印机密。

## 打印安全

P0 打印接受任意纯文本，而非任意文件。

控制措施：

- 最大文本大小：默认 20 KB。
- 最大页数：默认 5 页。
- 每队频率：默认每 10 分钟一次。
- 每队总计：默认 20 次。
- 审计文本哈希、页数、队伍、操作员、打印机、CUPS 任务 ID、请求 IP 与失败原因。

## 运维安全

- 在正式比赛前执行完整备份。
- 比赛期间执行计划备份。
- 在比赛日前验证恢复流程。
- 保存离线镜像 tar 文件与部署包校验和。
- 限制对部署主机的 shell 访问。
- 在 `backup-01` 或外部介质上保留备份副本。
